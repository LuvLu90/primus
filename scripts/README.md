# scripts

| 脚本 | 作用 |
|---|---|
| `build-core.mjs` | `agent-core` 里 `npm ci`，下载并校验锁定的模型目录后离线构建（`build:offline`）；组装 `dist/agent-core/`（最小运行产物 + Core 上游 MIT `LICENSE` + `manifest.json`），下载并校验 Node.js LTS 官方 zip、只解出 `node.exe` 与 `LICENSE` 到 `dist/runtime/`。参数：`--skip-install`、`--skip-build`、`--platform win-x64\|current` |
| `core-dist.mjs` | 上面两步共用的纯函数：SHA-256、`SHASUMS256.txt` 解析、最小 zip 读取与文件过滤、manifest 生成与校验（单测 `core-dist.test.ts`） |
| `node-runtime.json` | 内置 Node.js 运行时的锁定版本与固化哈希（发行包与解出文件） |
| `smoke-core-rpc.mjs` | 启动 `rpc-entry.js`（临时 HOME、离线），发送 `get_state`，校验收到成功 `response`；`--dist` 跑组装好的 `dist/agent-core`（先按 manifest 校验，复制到含中文与空格的临时安装目录，Windows 上用 `dist/runtime/node.exe`），`--entry` / `--node` 可指定入口与运行时 |
| `core-target.mjs` | 冒烟与契约测试共用：选择 Core 入口与运行时（`--dist` 时校验 manifest 并复制到含中文与空格的临时安装目录），以及薄壳启动 Core 的环境变量 |
| `contract-core-rpc.mjs` | `pnpm contract:core`：RPC 契约测试（技术方案第 23 章）。每条用例起一个真实 Core 进程与一个 Faux 模型服务，验证 `get_state`、`prompt`、`abort`（含停止生效 < 1 秒）的响应与事件，`multiturn` 用例验证同一会话两轮对话的上下文与历史，`resume` 用例模拟 `core_restart`（`--session-id` 新建、同一 ID 重新拉起后历史与上下文恢复），`stream` 用例（思考、文本、工具调用与第二次回复）检查流式不变量并交给桌面端会话 store 按不同批次重建，流式结果须与 `message_end` 一致（第 7.4 节）；`--dist`、`--entry`、`--node` 同冒烟（`--dist` 与 `--entry` 互斥），用例通过还要求关闭 stdin 后 Core 以 0 退出、stdout 无非法行，`--case <名称>` 只跑指定用例 |
| `core-contract/` | 契约测试的组件：`core-process.mjs`（拉起 Core、按 LF 分帧的 JSONL 读写、等待记录）、`faux-model.mjs`（127.0.0.1 上按 `anthropic-messages` 协议以 SSE 返回脚本化回复的 Faux 模型服务）；单测 `core-contract.test.ts` |
| `check-forbidden-sdk.mjs` | 被禁供应商 SDK 检查（C1，技术方案第 6.2 节）：锁文件依赖图、源码逐文件扫描、**导入图**（从 `forbidden-sdk.json` 的 `importGraph` 入口——前端页面、第一方扩展源码与 `primus-bundle.js`、Core 打包前入口与 `dist/agent-core` 产物入口——按 Node.js 解析规则遍历实际加载的文件，含第三方包内部，报告导入链）、**SBOM**（`dist/sbom/*.cdx.json` 中的全部组件）。`--strict` 要求入口与 SBOM 全部存在（CI 构建后使用；每个 glob 都须匹配到文件，`allowEmptyGlobs` 列出的预留模式除外），并输出各图无法解析的第一方导入；`--self-test` 构造经导入图传递引入、仅在 SBOM 中出现被禁 SDK 的临时夹具，确认检查以非零状态退出 |
| `import-graph.mjs` | 导入图解析（exports / imports 条件解析、别名、TS 源码 `.js`→`.ts`、跟随 pnpm/npm 工作区符号链接；跳过仅类型导入），单测 `import-graph.test.ts` |
| `generate-sbom.mjs` | `pnpm build:sbom`：用包管理器自带命令按锁文件生成 CycloneDX SBOM——`pnpm sbom`（工作区）→ `dist/sbom/primus-workspace.cdx.json`，`npm sbom`（agent-core）→ `dist/sbom/agent-core.cdx.json`；CI 上传为制品 `sbom-cyclonedx` |
| `forbidden-sdk.json` | 被禁包名规则、`enforceCore`、导入图入口与 SBOM 配置 |
| `check-tauri-imports.mjs` | 只允许 `src/lib/platform/tauri/` import `@tauri-apps/*` |
| `check-icons.mjs` | 图标规范（技术方案第 16.1.1 节“图标”）：前端不得 import `lucide-react` 等图标库；`apps/desktop/src/components/icons/` 里的颜色只能是 `currentColor` / `none`；`<Icon>` 上不写透明度、任意颜色与数值 `size` / `strokeWidth` / `fill`（单测 `check-icons.test.ts`） |
| `vendor-reicon.mjs` | 把 Reicon（MIT）的 Outline 图标收进 `apps/desktop/src/components/icons/icons.generated.ts`：读取手动下载解压的 `reicon-react` tarball（不引入依赖），按脚本内 `ICONS` 映射生成并校验颜色与线宽，之后用 Biome 格式化；来源与署名见该目录 `NOTICE.md` |
| `check-naming.mjs` | `agent-core/` 之外不得出现上游项目原始名称（第 1.3 节） |
| `cr-prereview.mjs` | 推送前 CodeRabbit CLI 本地预审（CLI 额度与 PR 审查额度分开）：`pnpm review:local` 手动审查当前分支相对 `origin/main` 合并基点的已提交改动（`PRIMUS_CR_BASE` 可改基准）；`pnpm hooks:install` 设 `core.hooksPath=.githooks` 启用 `pre-push` 自动预审。仅 critical / major 阻止推送；未装 CLI、限流或审查失败只提示不阻塞；跳过用 `PRIMUS_SKIP_CR=1 git push`（PowerShell：`$env:PRIMUS_SKIP_CR = "1"; git push; Remove-Item Env:PRIMUS_SKIP_CR`，推送后务必清除，否则后续推送都会跳过）或 `--no-verify`。待推送提交不是当前 HEAD 的引用无法审查，钩子拒绝推送；基准合并基点解析失败时停止预审、不改用其他分支。CLI 安装：PowerShell `irm https://cli.coderabbit.ai/install.ps1 \| iex`，再 `coderabbit auth login`（单测 `cr-prereview.test.ts`） |
| `check-versions.mjs` | 工具链（含 `node-runtime.json`）与依赖版本与 `version-baseline.json`（技术方案第 2.4 节）一致，且全部精确锁定、无预发布版 |
| `version-baseline.json` | 版本基线（含 CI 安装的 cargo-nextest、tauri-driver 版本，`check-versions.mjs` 校验 ci.yml 与之一致）；Renovate 月度 PR 会同步更新它 |
| `build-msi.mjs` | `pnpm build:msi`（仅 Windows；其他平台 `--dry-run` 查看命令）：`--arch x64\|arm64`（默认 x64）决定 Rust 目标（与 rustc 主机不同才加 `--target` 交叉编译）、`wix build -arch`、内置运行时平台（按 manifest 的 `runtime.platform` 校验）与文件名 `Primus_<ver>_<arch>_zh-CN.msi`；校验 `dist/agent-core` 与 manifest、扩展与 `node.exe` 就位、WiX 版本与基线一致 → `tauri build --no-bundle` → 签名 `Primus.exe` → 准备 WebView2 引导程序（缺失时从微软下载，校验微软 Authenticode 签名）→ `wix build`（WiX 7，`-culture zh-CN -acceptEula wix7`，`-bindpath app/core/runtime`，SemVer 按第 3.3.3 节映射为 `ProductVersion`：第三字段 = 修订 × 100 + 阶段偏移，alpha/beta/rc.N → N/30+N/60+N，稳定版 → 99，保证稳定版高于同版本预发布版）→ 签名 MSI → `.sha256` → `tauri signer sign --app-version <版本>` 生成 `.sig` 并用 `TAURI_SIGNING_PUBLIC_KEY` 按 updater 规则校验 → `signtool verify /pa` 校验 `Primus.exe`、`node.exe`、MSI（第 3.3.4 节）。构建前总会校验内置 `node.exe` 的 OpenJS 官方签名。代码签名需成对配置 `PRIMUS_SIGN_CERT_SHA1`、`PRIMUS_SIGN_TIMESTAMP_URL`（`signtool` 取 `PRIMUS_SIGNTOOL` 或 Windows SDK 中最新版本）；updater 签名需 `TAURI_SIGNING_PRIVATE_KEY`（内容）或 `TAURI_SIGNING_PRIVATE_KEY_PATH`（路径）加 `TAURI_SIGNING_PUBLIC_KEY`（公钥同时在 `tauri build` 时编译进 `Primus.exe`，供自动更新校验）；配一半拒绝构建，`PRIMUS_REQUIRE_SIGNING=1` 时两类签名缺一不可，`PRIMUS_REQUIRE_UPDATER_SIGNING=1`（发布）时 updater 签名必须配置。参数：`--version`（与 `tauri.conf.json` 不同时经 `tauri build --config` 同步给 `Primus.exe`；与 `--skip-tauri` 同用且版本不同则拒绝）、`--skip-tauri`（校验签名后写在 exe 旁的 `Primus.exe.build.json`：版本、架构、大小、修改时间须与本次一致，否则拒绝）、`--out-dir`、`--webview2`、`--dry-run`（单测 `build-msi.test.ts`） |
| `updater-signature.mjs` | 按 tauri-plugin-updater 的规则校验 `tauri signer` 生成的 minisign 签名（`.sig`）：密钥 ID、Ed25519 签名（预哈希 BLAKE2b-512 或原文）、trusted comment 全局签名，可要求绑定的 `version` 与安装包一致；`build-msi.mjs` 生成 `.sig` 后调用，也可单独运行 `node scripts/updater-signature.mjs <文件> [--pubkey <公钥>] [--version <版本>]`（单测 `updater-signature.test.ts`） |
| `gen-update-manifest.mjs` | 自动更新清单（技术方案第 3.6 节、ADR 0007）：发布作业用它按本次 Release 的 4 个安装包与 `.sig` 生成 Tauri 2 静态清单（`platforms` 含 `windows-x86_64-msi` / `windows-x86_64-nsis` / `windows-aarch64-msi` / `windows-aarch64-nsis`，`url` 指向本次 Release 附件，`signature` 为 `.sig` 内容，`notes` 取 Release 说明），上传到 Release `update-feed`。正式版写 `stable.json` 与 `beta.json`，预发布只写 `beta.json`；`--existing-stable` / `--existing-beta` 给出现有清单，版本更高的通道不覆盖，同一版本可覆盖；`--verify` 用 `TAURI_SIGNING_PUBLIC_KEY` 按 updater 规则校验每个 `.sig`。写出的文件名逐行打印到 stdout（单测 `gen-update-manifest.test.ts`） |
| `ci-signing-drill.ps1` | CI 签名演练：在 GitHub Actions 运行器上调用 `import-release-signing.ps1`（与发布相同的无 Secret 路径：临时自签名代码签名证书，导入本机受信任根与受信任发布者）并生成一次性 updater 密钥，写入签名环境变量与 `PRIMUS_REQUIRE_SIGNING=1`；另生成一张临时可导出证书导出为带随机口令的 PFX，经 `PRIMUS_SIGN_PFX_BASE64` / `PRIMUS_SIGN_PFX_PASSWORD` 再跑一遍导入脚本的 PFX 分支（之后签名用该证书，PFX 文件随即删除），让每次 CI 完整走签名与校验流程；产物只在该运行器受信任，不能分发 |
| `build-nsis.mjs` | `pnpm build:nsis`（仅 Windows；其他平台 `--dry-run`）：`tauri bundle --bundles nsis` 打包 `build-msi.mjs` 刚编译的同版本、同架构 `Primus.exe`（按 `Primus.exe.build.json` 校验，不重新编译）；临时配置把产品名设为「乾元 Primus」、把 `dist/runtime`、`dist/agent-core` 收进 `resources\runtime`、`resources\agent-core`（与 MSI 布局一致），其余 NSIS 设置（简体中文、按机器安装、内嵌 WebView2 引导程序、许可页、`windows/nsis/hooks.nsh` 给 `data` 授予 Users 修改）在 `tauri.conf.json`；输出 `out/Primus_<ver>_<arch>-setup.exe` 与 `.sha256`，配置了 updater 密钥时另对 setup.exe 执行 `tauri signer sign --app-version` 生成 `.sig` 并按 updater 规则校验（单测 `build-nsis.test.ts`）。配置了 `PRIMUS_SIGN_CERT_SHA1` / `PRIMUS_SIGN_TIMESTAMP_URL` 时经临时配置 `bundle.windows.certificateThumbprint` 让 tauri bundle 在改写 `Primus.exe` 后重新签名并签 setup.exe，随后 `signtool verify /pa /all` 校验两者；签名配置规则与 `build-msi.mjs` 相同 |
| `import-release-signing.ps1` | 发布构建（`release.yml`）准备代码签名证书：默认在 GitHub 托管运行器上临时生成本次发布专用的自签名证书（`-Version` 写进使用者名称，私钥不可导出、不保存，不入仓库也不用 Secret；每个版本证书不同，不生成 updater `.sig`）；以后有正式证书时读仓库 Secret `PRIMUS_SIGN_PFX_BASE64` / `PRIMUS_SIGN_PFX_PASSWORD` 导入 PFX（配一半报错，并写 `PRIMUS_REQUIRE_SIGNING=1` 要求 updater 密钥）。检查私钥、代码签名用途与有效期；自签名证书加入本机受信任根与受信任发布者，按 `-Arch` 导出本作业证书的公钥证书 `Primus-signing-cert-<x64\|arm64>.cer` 作为 Release 附件（每个架构的作业各自生成、各自导出）；写入 `PRIMUS_SIGN_CERT_SHA1`、`PRIMUS_SIGN_TIMESTAMP_URL` 与证书来源 `PRIMUS_RELEASE_CERT_SOURCE`（`generated` / `pfx`，发布说明据此描述证书范围） |
| `msi-smoke.ps1` | MSI 静默安装 → 检查安装布局（按 manifest 逐个校验 Core 文件哈希、`node.exe` 签名、卸载信息、开始菜单快捷方式）→ `data` 的 ACL 含 `BUILTIN\Users` 显式修改 (M) 且继承；有 gsudo 时以中完整性级别实际写入 `data`、并确认写不进安装目录根 → WebView2 检测 / 引导是否按预期 → 用安装目录的 `node.exe` 跑 Core RPC 冒烟 → 静默卸载，程序与快捷方式移除、`data` 及其中文件保留 → 清理。需管理员；参数 `-InstallDir`、`-KeepInstalled`、`-KeepData`、`-ExtraChecks`（卸载前调用的附加检查脚本）；CI 与安装测试虚拟机共用 |
| `install-matrix/` | 安装矩阵（CI 的 install-matrix 作业）：`prepare-location.ps1` 给出 Program Files 或新建的隔离 NTFS VHDX（优先 D，已占用时选择空闲盘符，不改现有卷）；`matrix-checks.ps1` 经 `msi-smoke.ps1 -ExtraChecks` 调用：启动常驻 Faux 模型服务（`faux-serve.mjs`），x64 用端到端测试 `e2e/specs/conversation.e2e.ts` 对安装后的 Primus.exe 完成一次含工具调用的对话，再新建标准用户经计划任务运行 `std-user.ps1`（启动 App、ACL 与隔离、`converse.mjs` 按薄壳方式拉起 Core 完成对话、数据不落到 data 之外）。WebView2 注册表覆盖探针由管理员设置和清理，标准用户只读取并验证，已有 Primus.exe 策略时拒绝覆盖 |
| `nsis-smoke.ps1` | NSIS 安装程序 `/S /D=` 静默安装 → 检查布局（按 manifest 校验 Core 文件哈希、`node.exe` 签名、卸载信息的显示名 / 版本 / 发布者、开始菜单快捷方式）→ `data` 的 ACL 与中完整性级别写入（有 gsudo 时）→ 安装目录中的 `node.exe` 跑 RPC 冒烟 → `uninstall.exe /S _?=` 卸载，程序与快捷方式移除、`data` 保留 |
| `install-acl-fixtures.ps1` / `install-acl-elevated.test.ps1` | MSI / NSIS 硬链接探针的可信目录用完整安全描述符替换所有者和 DACL，并回读核对；不能只用 `icacls /grant:r`，它会保留其他主体的显式授权。NSIS 正向冒烟也安装到此类已有目录。提权回归在 Windows x64 / ARM64 CI 中用 Windows PowerShell 5.1 执行生产准入函数，覆盖显式用户授权残留、可信非空目录保留、空不可信目录替换后的 Administrators 所有者和受保护只读 DACL；普通原生回归仍无需管理员权限 |
| `check-installers.ps1` | CI 与发布共用：`out/` 中某架构恰有一个 MSI 与一个 NSIS EXE、文件名版本与 `tauri.conf.json` 一致、< 120MB、`.sha256` 一致、MSI 平台为 `x64;2052` / `Arm64;2052`、`Primus.exe` 的 PE Machine 与架构一致；写入 `PRIMUS_MSI`、`PRIMUS_NSIS` |
| `vm/New-PrimusTestCheckpoint.ps1` | Hyper-V 宿主机上把安装测试虚拟机正常关机后建立 `clean` 检查点（可选启用来宾服务接口；同名已存在须 `-Force`），见 `vm/README.md` |
| `vm/Reset-PrimusTestVM.ps1` | 一键还原检查点 → 启动并等待检测信号与 PowerShell Direct → 复制 MSI 与 `msi-smoke.ps1` 进来宾（PowerShell Direct 或 Copy-VMFile）→ 可选执行冒烟 → 拉回日志；凭据用 `Get-Credential`，不硬编码。手工测试项见 `docs/安装测试清单.md` |
